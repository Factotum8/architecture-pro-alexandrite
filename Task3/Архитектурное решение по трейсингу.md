# Мотивация
В текущей архитектуре компании «Александрит» (CRM, MES, RabbitMQ, API для партнёров) отсутствует сквозная трассировка заказов.

Из-за этого возникают ситуации, когда заказ:
* «зависает» между сервисами (например, между MES и CRM);
* теряет сообщение в очереди RabbitMQ;
* обрабатывается с большими задержками без очевидных причин;
* имеет непонятный статус для пользователей и операторов.

Это приводит к росту количества жалоб и потере доверия со стороны партнёров.
Для устранения этой проблемы необходимо внедрить систему распределённого трейсинга, которая позволит видеть полную «жизнь» заказа — от приёма через API до производства и доставки результата в CRM.

Цели внедрения
* Восстановить прозрачность прохождения заказа через все сервисы.
* Быстро диагностировать, где именно заказ «застрял».
* Повысить стабильность и прогнозируемость SLA по заказам.
* Сократить время поиска и устранения инцидентов (MTTR).


# Анализ системы и точки трейсинга

Потенциальные точки потери или зависания:

1. API Gateway - ошибка при создании заказа, потеря корреляции
3. CRM	- ошибки при создании записи заказа, неверный статус
4. MES	- ошибка при расчёте, зависание worker-а, задержка публикации результата
5. MES Worker - таймаут или сбой при обработке 3D-модели
6. Интеграции - несогласованность статусов между MES и CRM

## Компоненты, которые должны быть покрыты трейсингом
1. API Gateway
2. CRM
3. MES Core
4. MES Worker Pool
5. RabbitMQ (через middleware-интеграцию с трейсингом)

## Данные, которые должны попадать в трейсинг

Каждый запрос / событие должен содержать следующие поля:

| Поле             | Назначение                                                             |
| ---------------- | ---------------------------------------------------------------------- |
| `trace_id`       | Глобальный идентификатор запроса / заказа                              |
| `span_id`        | Уникальный идентификатор операции внутри trace                         |
| `parent_span_id` | Родительская операция, для построения дерева вызовов                   |
| `service_name`   | Имя сервиса (CRM, MES, API Gateway и т.д.)                             |
| `operation_name` | Название операции (CreateOrder, CalculatePrice, PublishMessage и т.д.) |
| `status`         | Результат выполнения (`success`, `error`, `timeout`)                   |
| `duration_ms`    | Время выполнения операции                                              |
| `timestamp`      | Время начала операции                                                  |
| `correlation_id` | ID заказа или бизнес-события (для связки с CRM)                        |
| `error_message`  | Текст ошибки (если есть)                                               |
| `payload_size`   | Размер сообщения или данных в обработке                                |

## Предлагаемое решение

![Александрит.drawio.png](%D0%90%D0%BB%D0%B5%D0%BA%D1%81%D0%B0%D0%BD%D0%B4%D1%80%D0%B8%D1%82.drawio.png)

Для реализации распределённого трейсинга предлагается использовать OpenTelemetry как единый стандарт сбора и передачи данных.
В качестве backend-хранилища и визуализации — Jaeger.

Технологический стек:
1. OpenTelemetry SDK — интеграция в код CRM, MES, API Gateway.
2. OpenTelemetry Collector — агрегирует данные, нормализует и отправляет в backend.
3. Jaeger — хранилище и интерфейс для визуализации трейсингов.
4. Grafana — визуализация метрик и трассировок (через Tempo Data Source).
5. Correlation Middleware для RabbitMQ — автоматически добавляет trace_id в сообщения.

## Компромиссы
| Ограничение                    | Описание                                                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------ |
| MES — проприетарная часть кода | Некоторые компоненты MES написаны сторонним вендором; придётся дорабатывать через SDK или агент. |
| Высокая детализация трейсинга  | Может увеличивать объём логов и нагрузку на хранилище (до +30%).                                 |


## Безопасность и доступ
Меры внутри компании
1. Доступ в систему трейсинга (Jaeger/Grafana) только для сотрудников с ролями DevOps, Разработчик, Поддержка.
2. Аутентификация через корпоративный SSO (LDAP / OAuth2).
3. Разграничение прав по ролям: просмотр, администрирование, экспорт.
4. Шифрование соединений (TLS) между агентами и collector-ом.

### Внешние интеграции
1. trace_id и correlation_id не должны содержать бизнес-данные.
2. Внешним партнёрам доступ к системе трейсинга не предоставляется.
3. Для запросов внешних API trace-информация маскируется или агрегируется до бизнес-метрик.
