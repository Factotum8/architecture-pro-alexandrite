# Мотивация
В текущей архитектуре компании «Александрит» отсутствует централизованная система мониторинга. Это приводит к тому, что сбои в работе CRM, MES, очередей RabbitMQ и API становятся известны только после жалоб клиентов или операторов.
Рост нагрузки, интеграция с внешними партнёрами и увеличение числа заказов требуют от системы высокой наблюдаемости и прозрачности.
Добавление мониторинга позволит:
1. оперативно выявлять и устранять проблемы до того, как их замечают пользователи;
2. контролировать производительность ключевых сервисов (CRM, MES, RabbitMQ, API);
3. прогнозировать узкие места и планировать масштабирование;
4. улучшить SLA для партнёров и B2C-клиентов;
5. повысить доверие и прозрачность для бизнеса.

# Выбор подхода к мониторингу
Будем использовать комбинированный подход, объединяющий:
1. RED (Rate, Errors, Duration) — для API и сервисов, чтобы отслеживать частоту запросов, ошибки и время отклика;
2. USE (Utilization, Saturation, Errors) — для инфраструктурных ресурсов (CPU, память, диски, очередь RabbitMQ);
3. «Четыре золотых сигнала» — для пользовательских интерфейсов (дашборды MES и CRM), чтобы понимать восприятие системы конечными пользователями.

# Метрики и объекты мониторинга

## API (внешний и внутренний)
Метрики:

* request_rate — количество запросов в секунду.
Зачем: позволяет выявить пики нагрузки и прогнозировать масштабирование.
Ярлыки: endpoint, method, status_code, client_type.
* request_error_rate — доля неуспешных ответов (4xx, 5xx).
Зачем: контроль качества интеграций и стабильности API.
Ярлыки: endpoint, status_code.
* request_duration_seconds — время обработки запроса.
Зачем: измерение латентности и влияние нагрузки на скорость ответа.
Ярлыки: endpoint, method.

## RabbitMQ
Метрики:

* queue_messages_ready — количество сообщений в очереди.
Зачем: определяет текущую загрузку и «хвосты» в обработке заказов.
Ярлыки: queue_name.
* queue_consumers — количество активных воркеров.
Зачем: помогает понять, хватает ли ресурсов для обработки нагрузки.
Ярлыки: queue_name, region.
* queue_processing_time — среднее время жизни сообщения в очереди.
Зачем: отражает задержку в цепочке обработки.
Ярлыки: queue_name.

## MES (производственный контур)
Метрики:

* job_processing_time_seconds — время расчёта стоимости модели.
Зачем: ключевой показатель производительности MES.
Ярлыки: job_type, model_complexity.
* job_success_rate — доля успешно завершённых задач.
Зачем: оценка стабильности вычислительного кода.
Ярлыки: job_type.
* cpu_utilization / memory_usage — утилизация ресурсов.
Зачем: основа для autoscaling.
Ярлыки: instance_id, region.
* queue_waiting_time — среднее время ожидания задачи в очереди.
Зачем: показатель перегрузки системы.
Ярлыки: priority, queue_name.

## CRM
Метрики:

* order_create_latency — время от получения сообщения до создания заказа.
Зачем: измеряет задержку между MES и CRM, отражает SLA по созданию заказов.
Ярлыки: source_system, order_type.
* order_sync_errors_total — количество ошибок синхронизации статусов.
Зачем: выявление проблем интеграции с MES.
Ярлыки: error_type.

## Пользовательский интерфейс MES (операторский дашборд)
Метрики:

* page_load_time_seconds — среднее время загрузки первой страницы.
Зачем: показатель UX и скорости БД.
Ярлыки: page, status_filter.
* ui_error_rate — процент ошибок при загрузке данных.
Зачем: контроль деградации фронта и API.
Ярлыки: page, api_endpoint.
* active_sessions — количество активных операторов.
Зачем: помогает анализировать нагрузку на интерфейс.
Ярлыки: region, shift.

## Инфраструктура (серверы, контейнеры, БД)
Метрики:

* cpu_utilization, memory_usage, disk_usage — базовые показатели утилизации.
Зачем: прогнозирование масштабирования.
Ярлыки: service_name, instance_id.
* db_query_latency_seconds — среднее время выполнения SQL-запросов.
Зачем: индикатор нагрузки на БД.
Ярлыки: query_type, database.
* db_connections_active — число активных соединений.
Зачем: помогает выявить утечки коннектов.
Ярлыки: database, application.

## План действий

Это черновик технического задания и план реализации в течение 2–3 итераций.
### Этап 1 — Развёртывание базовой инфраструктуры мониторинга
1. Создать отдельный инстанс time-series базы данных (Prometheus или VictoriaMetrics) для хранения метрик.  
2. Развернуть Grafana как инструмент визуализации и дашбордов.  
3. Установить и настроить экспортеры:
   * node_exporter для серверов и контейнеров;
   * rabbitmq_exporter для очередей;
   * postgres_exporter для баз данных;
   * prometheus_client для приложений (CRM, MES, API Gateway);
   * blackbox_exporter для проверки доступности API.
4. Настроить сбор логов через Loki или ELK (для централизованного анализа инцидентов).

### Этап 2 — Интеграция метрик и алертинга
1. Добавить в код приложений метрики по выбранным подходам (RED/USE).
2. Включить экспозицию метрик через /metrics endpoint (Prometheus формат).
3. Настроить Alertmanager:
   * уведомления в Slack/Telegram/email при превышении порогов;
   * эскалации в зависимости от уровня (warning / critical);
   * шаблон тикета в системе задач (например, Jira).

### Этап 3 — Визуализация и дашборды
1. Создать дашборды:
   2. для MES (время расчёта, количество активных воркеров, очередь задач);
   3. для CRM (время создания заказа, ошибки интеграции);
   4. для RabbitMQ (глубина очередей, задержка сообщений);
   5. общий обзор SLA (end-to-end время обработки заказа).
6. Создать отдельный дашборд для руководства с агрегированными KPI:
   7. количество заказов в работе;
   8. средняя задержка по заказам;
   9. текущие SLA-отклонения.
