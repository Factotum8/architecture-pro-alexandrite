# Архитектурное решение по кешированию

## Проблемы

* Операторы жалуются на долгую загрузку первой страницы MES: дашборд с заказами по статусам, несмотря на фильтры и пагинацию.
* Производство может выдерживать 2× нагрузку, но заказы «зависают» и долго отображаются.
* Рост количества заказов и B2B API-клиентов увеличил нагрузку на MES и CRM.

## Кандидаты для кеширования

1. Список заказов для дашборда MES. Частые чтения: операторы постоянно обновляют список свежих заказов. Записи (изменение статуса) относительно реже.
2. Список заказов в CRM. Менеджеры часто открывают список заказов по статусам.
3. Справочники и редко меняющиеся данные. Типы материалов, цвета, базовые тарифы, типы огранки и т.п.
4. Результаты расчёта стоимости изделий. Расчёт дорогой по CPU и времени.


## Мотивация
Кеширование предлагается для решения следующих проблем:
1. Медленная первая страница MES
   2. Сейчас операторы видят дашборд с задержкой, либо страница «тормозит».
   3. Это снижает скорость реакции на новые заказы и влияет на мотивацию операторов (их вознаграждение зависит от взятого в работу заказа).
4. Избыточная нагрузка на базы данных MES и CRM
   5. Списки заказов по статусам — классический пример тяжёлых запросов при большой истории.
   6. Сейчас, фильтрация и пагинация не дают адекватного выигрыша → отсутствие кеша.
7. Защита от лавинообразной нагрузки при росте заказов и B2B API.
   8. При увеличении количества запросов от внешних партнёров и B2C-клиентов, оптимизация чтения (через кеш) уменьшает нагрузку на критичные сервисы и базы.
   9. Экономия ресурсов при повторных расчётах стоимости.
10. Для повторных запросов одинаковых моделей можно избежать повторного тяжёлого расчёта.

Обоснование:
Клиентское кеширование (в браузере, HTTP-кеш, ETag, Last-Modified) может немного помочь, но:
* У операторов MES несколько человек борются за новые заказы — они должны видеть свежий список.
* У каждого оператора свой браузер; клиентский кеш не уменьшит нагрузку на базу данных — лишь чуть уменьшит трафик.
Проблемы серверные: тяжёлые запросы к БД и медленная генерация списка заказов.
---
**Вводим серверный кеш (Redis или аналог) для списков заказов и справочников.**

## Паттерн кеширования
Выбор: для списков заказов и справочников — паттерн Cache-Aside.

Обоснование:
1. Гибкость и простота внедрения. Легко добавить на существующую архитектуру без сильной переработки кода.
   2. Модель данных в кеше может отличаться от модели данных в БД
   3. Подходит для read-heavy сценариев (списки заказов по статусам).
4. Согласованность данных
   5. Источник истины остаётся в БД.
   6. При сбое кеша система продолжит работать (хоть и медленнее), т.к. можно напрямую читать БД.

### Почему не Write-Through
Для нашего кейса главное — ускорить чтения, а не записи; Write-Through может замедлить обработку статусов без ощутимой выгоды.

### Почему не Refresh-Ahead
Кеш должен работать без ошибок, поскольку в случае ошибки это будет не сразу определено и приведёт к неконсистентности данных и чтению из базы. Нужна качественная система мониторинга, чтобы не оказаться с устаревшими данными.
Нам не критично латентность cache-miss.


## Стратегия инвалидации кеша
Комбинация: Инвалидация по ключу (программная)

При изменении статуса, создании/закрытии заказа:
* удаляем ключи списков по старому и новому статусу (например, orders:PRICE_CALCULATED:*, orders:MANUFACTURING_STARTED:* для первой страницы).
* Для справочников: при изменении справочника (редкий кейс) — удаление/обновление соответствующего ключа.

Временная инвалидация (TTL)  
Для списков заказов — небольшой TTL (например, 30–60 секунд), чтобы:
* ограничить время жизни потенциально неконсистентного кеша,
* получить баланс между свежестью и производительностью.

**Обоснование TTL**. 
* Если опираться только на TTL, операторы могут видеть устаревший список в течение всего периода TTL.
* Для сценария «кто первый взял заказ — тот и заработал» это плохо; заказ может уже быть в работе, а другой оператор ещё «видит» его как свободный.

**Обоснование программной инвалидация**
* Всегда есть риск не покрыть какой-то путь изменения данных → потенциальные «вечные» записи.
* TTL даёт «страховочную» границу жизни кеша.
