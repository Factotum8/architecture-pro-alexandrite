# Проблемы

## Отсутствие очереди при работе с API клиентов
Сейчас внешние клиенты обращаются к MES напрямую, минуя брокер сообщений.
Это приводит к неконтролируемому потоку запросов, пикам нагрузки и отсутствию механизма балансировки между воркерами MES.
Необходимо замкнуть API-клиентов на очередь сообщений (RabbitMQ), чтобы:
* упорядочить поток данных в единый канал;
* управлять скоростью обработки заказов;
* равномерно распределять задачи между MES-инстансами.

## Отсутствие централизованного мониторинга и алертинга
На данный момент нет системы мониторинга для ключевых сервисов (CRM, MES, RabbitMQ, API).
Из-за этого сбои в любом из компонентов остаются незамеченными до появления жалоб от пользователей.
Необходимо внедрить централизованный мониторинг (Prometheus + Grafana, ELK или аналог), чтобы:
* отслеживать доступность сервисов;
* собирать метрики производительности;
* настраивать алерты при деградации или недоступности компонентов.

## MES — узкое место в архитектуре
MES выполняет расчёты, которые могут занимать до 30 минут, при этом запущен в одном экземпляре без возможности горизонтального масштабирования.
Это делает его главным ограничением производительности всей системы. UI MES (дашборд) тормозит, потому что те же ресурсы используются для API.
Следует:
* вынести вычислительную часть в отдельный worker-пул;
* настроить autoscaling в облаке;
* разграничить API и расчётные задачи для лучшего управления нагрузкой.
* API Gateway с аутентификацией, rate limiting/quotas для партнёров. 

## Дашборд MES «вытягивает» весь объём данных
Даже с пагинацией — если запрос фильтрует по статусам и сортирует по дате — он делает full scan.
Нет индексов по status, created_at.
Нет кэширования (например, Redis).
Каждое обновление UI тянет сотни тысяч строк из БД.
Рекомендуется оптимизировать запрос на дашборде:
* добавить индекс (status, created_at DESC);
* ограничить выборку LIMIT 100;
* использовать материализованный вид или Redis-кэш.

## Низкая скорость и высокая инерционность релизного цикла
Задержки при релизах достигают одного месяца, что замедляет внедрение улучшений и фиксов.
Отсутствие автоматизированного тестирования повышает риск дефектов и делает релизы тяжёлыми.
Рекомендуется:
* внедрить автоматическое тестирование (юнит-, интеграционное, e2e);
* перейти на короткий релизный цикл (1–2 раза в неделю);
* минимизировать размер релизов, чтобы упростить тестирование и возможный откат.

# Решения

## «Потушить пожар»
Добавить асинхронность в расчёт стоимости:
1. MES при получении 3D-модели кладёт задачу в очередь, возвращает task_id;
2. CRM периодически опрашивает статус расчёта;
3. результат — отдельное событие (price_calculated).

Оптимизировать запрос на дашборде:
1. добавить индекс (status, created_at DESC);
2. ограничить выборку LIMIT 100;
3. использовать материализованный вид или Redis-кэш.

RabbitMQ:
1. ограничить TTL для сообщений о расчётах;
2. добавить Dead Letter Queue.  

Низкая скорость и высокая инерционность релизного цикла:
* внедрить автоматическое тестирование (юнит-, интеграционное, e2e);
* минимизировать размер релизов, чтобы упростить тестирование и возможный откат.

Поставить мониторинг (RabbitMQ + PostgreSQL/MES):  
прометей-экспортер, алерты по количеству сообщений / времени обработки.

## «Архитектурное лечение»

Вынести расчёты из основного MES в отдельный сервис (pricing-service):
1. простой микросервис с очередью задач;
2. можно масштабировать горизонтально.

Ввести брокер уровня «оркестрации» заказов:
1. CRM не ждёт MES;
2. MES публикует события (OrderCreated, OrderReady, OrderFailed);
3. все сервисы реагируют на события независимо.

Добавить rate limiting на внешний API:
1. ограничить запросы по партнёрам;
2. добавить очередь ожидания.

Ввести SLA-мониторинг:
1. метрики по времени создания/обработки заказа;
2. метрики по расчёту стоимости;
3. алерты при превышении.
