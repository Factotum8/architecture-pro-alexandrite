# Архитектурное решение по логированию

## Из каких систем собираем логи
Централизованно логировать будем бэкенды и инфраструктуру.

1. Онлайн-магазин backend (Spring Boot) — application + access.
2. CRM backend (Spring Boot) — application + audit.
3. MES backend (C#) — application + audit.
4. RabbitMQ — системные/инфраструктурные логи (состояние очередей, ошибки публикации/доставки).
5. Базы данных (Online, CRM, MES) — slow query logs, ошибки.
6. Ingress/Load Balancer — HTTP access logs.
---
7. Фронтенды (Vue/React) — только минимальные технические логи в браузере; централизованно логировать будем бэкенды и инфраструктуру.

## Какие логи нужно собирать (уровень INFO)

Все логи — структурированные JSON с обязательными полями:
1. ts — время (ISO8601)
2. level — уровень логирования
3. service — online-store, crm, mes, rabbitmq, db-online, db-crm, db-mes
4. env — dev / release / prod
5. trace_id, span_id — для связи с трейсингом
6. order_id (если применимо)
7. correlation_id (для внешних B2B API)

### Типы логов уровня INFO

#### Логи Онлайн-магазина 
* Создание и движение заказа до отправки на расчёт
* Взаимодействие с MES / API
* Статусы заказа в онлайне

#### Логи CRM 
Статусы, которыми управляет CRM:
* MANUFACTURING_APPROVED
* CLOSED

#### Логи MES
Статусы MES
Логи UI-дэшборда операторов (для медленной главной страницы)

#### Базы данных
* Запросы, связанные с:
  * выборкой заказов по статусам в MES (главный дэшборд),
  * выборкой самых новых заказов.
* Ошибки

### Другие уровни логирования и когда их использовать
**DEBUG**
Подробный контекст: 
* промежуточные данные, тело сообщений, технические детали расчёта.
* Включаем только в dev и частично в release (по флагам или sampling).
* В prod — только временно при расследованиях (по feature-flag и с маскированием чувствительных данных).

**WARN**
Деградации:
* превышение целевого времени расчёта (например, > 10 минут),
* рост времени генерации дэшборда MES,
* повторные попытки отправки сообщений в MQ,
* мягкие ошибки внешних систем, которые будут ретраиться.

**ERROR**
Ошибки, приводящие к невозможности выполнения операции:
* не удалось расчитать стоимость,
* не удалось создать заказ в CRM,
* потеря/ошибка обработки сообщения MQ (после исчерпания ретраев),
* исключения при изменении статуса.

**FATAL** (или CRITICAL)
* Невозможность запустить сервис (ошибка конфигурации, критическая ошибка подключения к DB/MQ),
* Такие события должны триггерить немедленный алерт.

## Мотивация
Зачем вводить централизованное логирование
* Сейчас жалобы клиентов (B2C и B2B) и медленный MES говорят о том, что система работает нестабильно, а понимания, где именно возникают проблемы, нет.
* Производство может справиться с 2× ростом, но заказы «теряются» и «зависают» — проблема в IT-процессах.
* Без нормальных логов и трейсинга невозможно:
* отслеживать путь заказа от INITIATED до CLOSED;
* понять, где он «застрял» (MES, CRM, MQ);
* нормировать SLA и SLO.

## Предлагаемое решение (архитектура логирования)

### Стек

Формат логов:  
`JSON, единая схема ключей (ts, level, service, env, trace_id, order_id, …).`

Сбор логов:  
Агент на каждом EC2 (например, Fluent Bit или Vector).

Транспорт/обогащение:  
OpenTelemetry Collector — нормализация, добавление полей, маршрутизация.

Хранилище:  
Loki (экономичный, удобен с Grafana).

Просмотр и анализ:  
Grafana (LogQL / дашборды, алерты)

### Политика безопасности логов

Чувствительные данные:  
Не логировать открытые персональные данные (ФИО, email, телефон, адрес, платежные реквизиты).

Вместо этого:  
customer_id_hash, recipient_hash — хэш от идентификатора.   
Маскирование частей номеров (пример: ****1234).  
Удаление/маскирование таких полей на уровне приложений или агентов (Fluent Bit/Vector фильтры).

Доступ к логам. Разграничение прав по ролям:
* Разработчики — read-only к техническим логам dev/release, ограниченный доступ к prod.
* SRE/DevOps — полный доступ к техлогам.
* Безопасность/аудит — доступ к audit-логам.
---
* Аудит доступа к логам (кто и какие запросы выполнял).

###  Политика хранения логов
Индексация / разделение:  
По окружениям: logs-prod-*, logs-release-*, logs-dev-*.

По доменам:  
orders, billing/price, mes-dashboard, integration-mq, auth (опционально), infra-db.

Сроки хранения (ретеншн):  
Технические логи prod: 30 дней, release: 14 дней, dev: 7 дней.

Access-логи:  
14–30 дней (зависит от требований).
Audit-логи (изменения статусов, B2B, деньги): 90–180 дней (или больше — по регуляторике).

Объём:  
Планировать 1–3% от общего трафика/объёма данных.
По мере роста — перевод старых логов в «холодное» хранилище (S3/архивный индекс).

## Система анализа логов

### Алертинг
Примеры алертов:  

* **Ошибки в цепочке заказов:**
  * Увеличение количества ERROR в MES/CRM по событиям изменения статусов.
  * Отсутствие переходов заказов из SUBMITTED в PRICE_CALCULATED за N минут.
* **Проблемы с расчётом стоимости:**
  * p95 price_calculation_completed.calc_duration_sec > X минут.
  * Рост доли ошибок при расчёте.
* **MQ:**
  * Длина очередей MES↔CRM превышает порог.
  * Время в очереди (latency_ms между publish и consume) > N секунд.
* **MES-дэшборд:**
  * p95 mes_dashboard_query.latency_ms > X секунд.
* **Инциденты B2B:**
  * Резкий рост b2b_client_complaint_registered.

Алерты интегрируются в Slack/почту/мессенджеры + систему инцидент-менеджмента (Jira и т.п.).


## Критерии выбора технологии для логов

Loki 
**Стоимость владения** 
Loki: индексируются только метки, дешёвое хранение — хорошо для большого потока логов.
**Производительность и масштабируемость**
Loki: хорошо масштабируется по записи, оптимален для «огромного объёма логов + простые запросы».
**Функциональность поиска и аналитики**
Loki (LogQL): фильтрация по меткам + простой парсинг.
**Сложность эксплуатации**
Loki: просто поднять и поддерживать, хороший вариант «стартовать быстро».
**Интеграции и экосистема**
Loki хорошо интегрируются с Grafana, OTel, Fluent Bit.
